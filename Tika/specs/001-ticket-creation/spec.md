## User Scenarios & Testing *(mandatory)*

### User Story 1 - 새 티켓 빠르게 등록 (Priority: P1)

할 일이 떠올랐을 때 제목만으로 티켓을 즉시 등록해 Backlog에 추가할 수 있다.

**Why this priority**: 아이디어를 놓치지 않고 기록하는 것이 앱의 핵심 가치이며, 상태 이동·수정·완료 등 다른 모든 기능의 전제 조건이다.

**Independent Test**: 제목만 입력해 티켓을 등록하고, 생성된 티켓이 Backlog 컬럼에 나타나는지 확인하는 것만으로 완전히 검증 가능하며 그 자체로 가치를 전달한다.

**Acceptance Scenarios**:

1. **Given** 보드가 비어있음, **When** 사용자가 제목만 입력하고 등록, **Then** 티켓이 Backlog 컬럼에 생성되고 우선순위는 기본값(보통)으로 설정된다
2. **Given** 이미 Backlog에 티켓이 있음, **When** 사용자가 새 티켓을 등록, **Then** 새 티켓이 기존 티켓보다 먼저(맨 위) 보이도록 정렬된다

---

### User Story 2 - 상세 정보와 함께 등록 (Priority: P2)

사용자가 제목 외에 설명, 우선순위, 시작예정일, 종료예정일까지 함께 입력해 중요도와 기한을 명확히 할 수 있다.

**Why this priority**: 단순 등록만으로는 우선순위/기한 관리가 안 되며, 이후 마감 초과 인지·완료 확인 등 다른 기능의 기반이 된다.

**Independent Test**: 모든 선택 필드를 채워 등록한 뒤, 조회 시 입력한 값이 그대로 저장되어 있는지 확인.

**Acceptance Scenarios**:

1. **Given** 사용자가 설명/우선순위/시작예정일/종료예정일을 모두 입력, **When** 등록, **Then** 입력한 값이 그대로 저장되어 조회 가능하다
2. **Given** 사용자가 종료예정일로 오늘 이전 날짜를 입력, **When** 등록 시도, **Then** 등록이 거부되고 날짜를 다시 선택하라는 안내를 받는다

---

### User Story 3 - 잘못된 입력으로부터 보호 (Priority: P3)

사용자가 제목을 비우거나 너무 길게 입력하는 등 실수했을 때 명확한 안내를 받아 바로 고칠 수 있다.

**Why this priority**: 데이터 무결성을 지키고, 등록이 실패한 이유를 사용자가 즉시 이해하게 한다.

**Independent Test**: 제목 누락/공백/글자수 초과, 설명 글자수 초과, 잘못된 우선순위 값 등 각 케이스로 등록을 시도해 매번 이해 가능한 안내를 받는지 확인.

**Acceptance Scenarios**:

1. **Given** 제목을 입력하지 않음, **When** 등록 시도, **Then** "제목을 입력해주세요" 안내와 함께 등록이 거부된다
2. **Given** 제목에 공백만 입력, **When** 등록 시도, **Then** 동일한 안내와 함께 등록이 거부된다
3. **Given** 정의되지 않은 우선순위 값을 입력, **When** 등록 시도, **Then** 허용된 우선순위 값 목록을 안내받는다

---

### Edge Cases

- 제목이 정확히 200자일 때는 허용되고, 201자부터 거부된다
- 설명이 정확히 1000자일 때는 허용되고, 1001자부터 거부된다
- 종료예정일이 "오늘"과 정확히 같으면 거부된다 (오늘 이후만 허용, 당일 미포함)
- 시작예정일만 입력하고 종료예정일은 입력하지 않아도 등록이 허용된다

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 사용자가 제목만으로 새 티켓을 등록할 수 있게 해야 한다
- **FR-002**: 시스템은 신규 등록된 티켓의 상태를 항상 "Backlog"로 두어야 한다
- **FR-003**: 시스템은 사용자가 선택적으로 설명, 우선순위(낮음/보통/높음), 시작예정일, 종료예정일을 함께 입력할 수 있게 해야 한다
- **FR-004**: 시스템은 우선순위를 지정하지 않으면 "보통"을 기본값으로 적용해야 한다
- **FR-005**: 시스템은 제목이 비어있거나 공백만 있거나 200자를 초과하면 등록을 거부하고 이유를 안내해야 한다
- **FR-006**: 시스템은 설명이 1000자를 초과하면 등록을 거부하고 이유를 안내해야 한다
- **FR-007**: 시스템은 정의되지 않은 우선순위 값이 입력되면 등록을 거부하고 허용 값을 안내해야 한다
- **FR-008**: 시스템은 종료예정일이 오늘보다 이전이면 등록을 거부하고 이유를 안내해야 한다
- **FR-009**: 시스템은 새로 등록된 티켓이 Backlog 내에서 가장 먼저(맨 위) 보이도록 정렬해야 한다
- **FR-010**: 시스템은 등록된 각 티켓에 생성 시각과 마지막 수정 시각을 기록해야 한다

### Key Entities *(include if feature involves data)*

- **Ticket**: 사용자가 등록하는 할 일 단위. 제목(필수), 설명(선택), 상태(등록 시 항상 Backlog), 우선순위(낮음/보통/높음, 기본 보통), 시작예정일(선택), 종료예정일(선택, 오늘 이후만), 생성/수정 시각을 가진다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 사용자는 제목만 입력해 몇 초 안에 새 티켓을 등록할 수 있다
- **SC-002**: 잘못된 입력(빈 제목, 글자수 초과, 잘못된 우선순위, 과거 종료예정일) 시도는 100% 사용자가 이해 가능한 안내로 이어진다
- **SC-003**: 등록된 티켓은 사용자가 입력한 값과 항상 정확히 일치하게 저장된다 (데이터 유실 없음)
- **SC-004**: 새로 등록한 티켓은 등록 즉시 보드의 Backlog에서 확인 가능하다
